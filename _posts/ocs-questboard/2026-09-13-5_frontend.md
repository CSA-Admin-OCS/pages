# Phase 4: Frontend Integration

## What I Built

For Phase 4, I connected my Quest Board frontend to my Spring Boot REST API. My project uses **Option A**, which means the frontend is hosted on my GitHub Pages portfolio while the backend is handled separately by Spring Boot.

The frontend allows users to interact with quests without needing to use Postman. Users can view quests, create new quests, view details, and update existing quests.

This allows my frontend to communicate with the backend through the REST endpoints I created during Phase 3.

## Frontend Structure

Since my portfolio is a Jekyll site, I created the Quest Board page as a Jekyll page instead of making a separate standalone HTML website.

The relevant files are located in the following locations:

```text
assets/js/questboard/config.js
assets/js/questboard/questboard.js

_posts/ocs-questboard/2026-09-13-questboard.md
```

The actual Quest Board interface is located at:

```text
/questboard/
```

These pages do not conflict because each one has a different permalink.

## The Interface

The frontend contains a form for creating quests.

The form includes:

- Quest title
- Description
- Difficulty dropdown
- XP
- Status dropdown
- Deadline

I used dropdowns for values such as difficulty and status to make sure the user is using the correct options.

The page also has buttons to refresh the quest list, view details, and edit quests.

## Configuring the Backend URL

I created a separate `config.js` file to store the URL of my Spring Boot backend.

```javascript
const API_BASE_URL = "http://localhost:8585/api/questboard";
```

This is useful because the frontend JavaScript does not have to contain the backend URL in multiple places.

If my backend is eventually deployed to a different server, I only need to change the URL in `config.js`.

For example, I could change:

```javascript
const API_BASE_URL = "http://localhost:8585/api/questboard";
```

to the deployed backend URL without having to rewrite the rest of my JavaScript.

## Fetching Quest Data

I used JavaScript's `fetch()` function to communicate with my Spring Boot REST API.

When the Quest Board page loads, the `loadQuests()` function sends a GET request:

```javascript
async function loadQuests() {
    const response = await fetch(API_BASE_URL);
    const quests = await response.json();
}
```

The API returns the quests as JSON. JavaScript then loops through the returned objects and creates HTML elements to display them.

The frontend therefore follows this process:

```text
Page Loads -> loadQuests() -> GET /api/questboard -> Spring Boot -> JSON response -> JavaScript displays quests
```

## CORS

Because my frontend and backend are running on different origins, the browser's same-origin security rules can prevent the frontend from communicating with the backend.

I handled this in my Spring controller using:

```java
@CrossOrigin
```

This allows the GitHub Pages frontend to make requests to my Spring API.

The communication therefore works like:

```text
GitHub Pages                                Spring Boot
https://my-github-pages-site/ -> fetch() -> http://localhost:8585/api/questboard
```

For local development, my backend uses `localhost:8585`. When I eventually deploy the backend, I will update `config.js` with the deployed API address.

## Testing

I tested the REST API independently in Postman during Phase 3. For Phase 4, I used the same endpoints from the browser through JavaScript.

The main operations are:

| Operation       | HTTP Method | Endpoint               |
| --------------- | ----------- | ---------------------- |
| View all quests | GET         | `/api/questboard`      |
| View one quest  | GET         | `/api/questboard/{id}` |
| Create quest    | POST        | `/api/questboard`      |
| Update quest    | PUT         | `/api/questboard/{id}` |

The frontend uses `fetch()` to call these endpoints and then displays the returned JSON data.
