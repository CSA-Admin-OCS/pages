# Phase 3: Questboard Backend Implementation & Testing

## 1. Endpoint Pattern

For my Questboard project, I chose **Option A: GitHub Pages Frontend with a Spring Boot REST API**.

My frontend will be hosted through GitHub Pages, while the Spring Boot application handles the backend and database. Because the frontend and backend are separate, I use REST API endpoints to communicate between them using HTTP requests and JSON.

My Questboard API uses the following endpoints:

| HTTP Method | Endpoint               | Purpose                  |
| ----------- | ---------------------- | ------------------------ |
| GET         | `/api/questboard`      | Retrieve all quests      |
| GET         | `/api/questboard/{id}` | Retrieve one quest       |
| POST        | `/api/questboard`      | Create a new quest       |
| PUT         | `/api/questboard/{id}` | Update an existing quest |
| DELETE      | `/api/questboard/{id}` | Delete a quest           |

The API returns JSON instead of rendering HTML pages. This makes it possible for my GitHub Pages frontend to request and modify Questboard data without needing Thymeleaf templates.

## 2. REST Controller

I created a `QuestboardApiController` to handle HTTP requests.

```java
package com.open.spring.mvc.questboard;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@CrossOrigin
@RequestMapping("/api/questboard")
public class QuestboardApiController {

    private final QuestboardJpaRepository repository;

    public QuestboardApiController(QuestboardJpaRepository repository) {
        this.repository = repository;
    }

    @GetMapping
    public ResponseEntity<List<Questboard>> getAllQuests() {
        return ResponseEntity.ok(repository.findAll());
    }

    @GetMapping("/{id}")
    public ResponseEntity<Questboard> getQuest(@PathVariable Long id) {
        return repository.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<Questboard> createQuest(@RequestBody Questboard quest) {
        Questboard savedQuest = repository.save(quest);
        return ResponseEntity.status(HttpStatus.CREATED).body(savedQuest);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Questboard> updateQuest(
            @PathVariable Long id,
            @RequestBody Questboard quest) {

        if (!repository.existsById(id)) {
            return ResponseEntity.notFound().build();
        }

        quest.setId(id);
        Questboard updatedQuest = repository.save(quest);

        return ResponseEntity.ok(updatedQuest);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteQuest(@PathVariable Long id) {

        if (!repository.existsById(id)) {
            return ResponseEntity.notFound().build();
        }

        repository.deleteById(id);
        return ResponseEntity.noContent().build();
    }
}
```

The controller is marked with `@RestController`, which tells Spring that the methods return data directly rather than returning a webpage template.

I used `@RequestMapping("/api/questboard")` to create the base URL for all of my endpoints.

`@GetMapping`, `@PostMapping`, `@PutMapping`, and `@DeleteMapping` determine which HTTP requests are handled by each method.

For example:

```java
@GetMapping
public ResponseEntity<List<Questboard>> getAllQuests()
```

handles:

```text
GET /api/questboard
```

The method returns a `ResponseEntity<List<Questboard>>` because multiple Questboard objects are returned as a JSON list.

For retrieving an individual quest, I use:

```java
@GetMapping("/{id}")
public ResponseEntity<Questboard> getQuest(@PathVariable Long id)
```

`@PathVariable` takes the ID from the URL and passes it into the method. For example:

```text
GET /api/questboard/1
```

passes `1` into the `id` parameter.

For creating a quest, I use:

```java
@PostMapping
public ResponseEntity<Questboard> createQuest(@RequestBody Questboard quest)
```

`@RequestBody` converts the JSON sent by the frontend into a Java `Questboard` object.

The controller also uses `@CrossOrigin`. Since my frontend will be hosted separately on GitHub Pages, CORS support allows the frontend to make requests to my Spring Boot backend.

## 4. JPA Repository

I created a `QuestboardJpaRepository` to connect my controller to the database:

```java
package com.open.spring.mvc.questboard;

import org.springframework.data.jpa.repository.JpaRepository;

public interface QuestboardJpaRepository extends JpaRepository<Questboard, Long> {
}
```

The repository extends:

```java
JpaRepository<Questboard, Long>
```

The first type parameter tells Spring that this repository works with the `Questboard` entity. The second parameter tells Spring that the entity's ID is a `Long`.

One useful part of Spring Data JPA is that I don't have to manually write SQL queries for basic CRUD operations.

For example:

```java
repository.findAll();
```

retrieves all Questboard records.

```java
repository.findById(id);
```

retrieves a Questboard by its ID.

```java
repository.save(quest);
```

creates or updates a Questboard.

```java
repository.deleteById(id);
```

deletes a Questboard.

Spring Data JPA generates the necessary database operations based on the repository methods and my entity mappings.

This keeps my controller much simpler because I don't have to manually write SQL for every API request.

## 5. Error Handling

I also included error handling for cases where a requested Questboard object does not exist.

For example, when getting a quest by ID:

```java
return repository.findById(id)
        .map(ResponseEntity::ok)
        .orElse(ResponseEntity.notFound().build());
```

If the quest exists, the API returns:

```text
200 OK
```

with the Questboard JSON.

If it does not exist, the API returns:

```text
404 Not Found
```

I also check whether an object exists before updating or deleting it.

For an update:

```java
if (!repository.existsById(id)) {
    return ResponseEntity.notFound().build();
}
```

For a deletion:

```java
if (!repository.existsById(id)) {
    return ResponseEntity.notFound().build();
}
```

This prevents the API from pretending that an update or deletion succeeded when the requested ID doesn't exist.

For a successful POST request, I return:

```text
201 Created
```

instead of a normal `200 OK`, because a new resource was created.

For a successful DELETE request, I return:

```text
204 No Content
```

because the resource was successfully deleted and there is no object that needs to be returned.

These HTTP status codes make it easier for the GitHub Pages frontend to understand what happened when it communicates with the backend.

## 6. REST vs MVC

I chose **REST** instead of MVC because my frontend is hosted on GitHub Pages.

With MVC, Spring Boot would be responsible for rendering HTML pages using Thymeleaf. The frontend and backend would therefore be more tightly connected.

REST is a better fit for my project because GitHub Pages can host my frontend independently while Spring Boot provides the data through an API.

Furthermore, I'm really interested in learning more about using the Spring REST API, and want to use this project as a chance to get more experience with this tool.
